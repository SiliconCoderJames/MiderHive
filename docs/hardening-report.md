# 第三轮 · 全局核心审查（2026-09-08）

对核心层约 4000 行做 /W4 严格警告编译 + 全量人工通读 + 专项检查（线程安全 / SQL 绑定 / 鉴权一致性），
修复与结论如下：

## 发现与修复

| 类别 | 问题 | 修复 |
|---|---|---|
| 线程安全（死锁） | `shutdown()`/`stopHttpServer()` 持 `recursive_mutex` 等待 HTTP 线程 join，在途请求 handler 又在等这把锁——退出时有在途请求即互相等待 | 锁内取出 `http_`（`unique_ptr` 所有权转移），**锁外** `stop()` 排空请求后再重入关库 |
| 跨进程一致性 | `memory.set` 与 `knowledge.addVersion` 为“查-改-插”三步无事务：GUI 与 platformd 双进程并发写同库可产生两条 `is_latest=1` | 以 `BEGIN IMMEDIATE` 包裹全部三步，任一步失败回滚。双进程实测：60 次并发写，60 个版本无重复无断层 |
| 输入健壮性 | HTTP 层 5 处 `std::stoi(limit)` 对非数字抛异常；`tags` 非字符串元素、`budget` 非数字类型抛异常；库内存储 JSON（schema/params/audit detail）损坏时 `json::parse` 抛异常 | `parseLimit` 统一校验（非法 → 400）；tags 逐项 `is_string`；budget `is_number`；`safeStoredJson` 退化为原字符串 |
| 语义质量 | 嵌入器设计了词间分隔符（`kSep`）但从未使用——“AB C”与“A BC”跨词 n-gram 同哈希 | 空白折叠为分隔符码点参与哈希；provider 名升级 `ngram-hash-v2`（向量与 v1 不兼容） |
| 输入校验 | Agent 名长度无上限 | `1..64` 字符且禁止空白 |
| 索引 | GUI 按动作筛选审计时全表扫描 | 补 `idx_audit_action(action, created_at)`（schema 幂等执行，存量库自动生效） |
| 警告 | /W4 下 C4996/C4100/C4189 | `_CRT_SECURE_NO_WARNINGS`（本机场景预期用法）+ 未引用参数处理；核心层 /W4 零警告 |

## 验证汇总（本轮）

- 单元测试：**149 checks / 0 failures**（新增 4 项 HTTP 健壮性断言：`limit=abc`/`limit=-5`/tags 非字符串/budget 非数字 → 400）
- ASan：**149 checks / 0 报告**（含本轮全部修复）
- 集成验证：**39/39 通过**（feasibility_check.py，兼容 `MIDERHIVE_MASTER_KEY` 及旧名）

# 检索路径性能测量（2026-09-14，一次性本机测量）

测量工具：[scripts/bench_search.py](../scripts/bench_search.py)（隔离数据目录 + 独立 platformd，
1 万条知识条目，每条路径预热 5 轮后计时 30 轮，HTTP 全链路含鉴权）。
**与本文其他数字一样，这是一次性的本机测量，没有可复现的 CI 任务，请按"测过一次"理解。**

| 路径（1 万条，limit=20） | P50 | P95 | max |
|---|---|---|---|
| keyword ≥3 码点（FTS5 trigram） | 34.9 ms | 51.3 ms | 53.0 ms |
| keyword 2 码点（LIKE 回退） | 31.8 ms | 48.8 ms | 48.8 ms |
| semantic（384 维 vec0 kNN） | 32.6 ms | 50.1 ms | 51.5 ms |

## 诚实的结论

1. **三条路径的耗时几乎相同**（34.9 / 31.8 / 32.6 ms P50）——在这个量级上差异落在噪声里。
   *更正*：本报告初版把这三个数字解读成"~35–50ms 的请求地板（HTTP + JSON + 鉴权 + 全局锁）"，
   并据此断言"验收阈值定错了对象"。**那个解读是错的**：分层测量（见下文"延迟诊断"）显示
   服务端 p50 只有 0.2–0.3 ms，这三个数字是 **1 万行下的最坏情况查询**（bench 用的查询词
   命中全部 1 万条）叠加小样本离群值。正确的表述是：该量级下三条路径都还贴着**数据量**
   而非**请求链路**，所以彼此看不出差距。
2. 因此**"FTS5 比 LIKE 快"在这个量级上没有可测量的证据**。它的收益是结构性的：单次查询的
   工作量从"随正文总量线性增长的全表扫描 + 逐行回表（N+1）"变为"索引查询 + 一次批量取回"，
   只有在数据量大得多（10 万行级）或单条正文大得多时才会显现。消掉 N+1 这一点已经落地。
3. 验收标准里写的"keyword P95 < 50ms（1 万条）"实测 51.3ms，**在噪声边缘**——该阈值本身
   没有区分力（三条路径都在 48–53ms）。脚本保留 `--assert-p95-ms` 开关供手动对比，
   默认不断言：拿一个测不出差异的阈值当门禁只会制造假绿灯。

## 后续若要真正优化

* 重新设计基准：查询词要有选择性（命中几十条而不是全部 1 万条），否则测的是"全表 + 全命中装配"。
* 大数据量场景的 FTS 收益：把 `--rows` 提到 10 万再测，届时 LIKE 与 FTS 的差距才会拉开。

## 延迟诊断：地板在哪里（2026-09-14 补充）

上表的"P95≈50ms"容易被读成"服务端很慢"。用 [scripts/diag_latency.py](../scripts/diag_latency.py)
分层测量后（同一台机器，60 次/组）：

| 组 | avg | p50 | p95 | min |
|---|---|---|---|---|
| `/api/health` 每次新建连接 | 3.2 ms | **0.3 ms** | 32.0 ms | 0.1 ms |
| `/api/health` keep-alive | 3.6 ms | **0.2 ms** | 30.4 ms | 0.1 ms |
| semantic 空库 keep-alive | 6.0 ms | **0.3 ms** | 31.1 ms | 0.2 ms |

结论三条：

1. **服务端单请求成本 p50 只有 0.2–0.3 ms**——此前"约 40ms 请求地板"的说法是错的，
   那是 30 个样本的小样本效应叠加离群值造成的误读。
2. **约 5% 的请求出现 ~30 ms 的间歇性停顿**，三组数值一致（与检索无关）。
   原因**尚未定位**；候选：本机负载/调度（测量时该机器同时在跑构建与其它任务）、
   httplib 默认线程池行为。需要在**空闲机器**上复跑 `diag_latency.py` 才能定性。
3. 1 万行时检索本身约 30–35ms——但注意 bench 的查询词命中了**全部** 1 万条，
   属于最坏情况；选择性查询会快得多。该成本随数据量线性增长。

# 并发写入扩展性：全局锁到底是不是瓶颈（2026-09-14 测量 + 判定）

**被检验的缺陷**：Platform 的写路径共用一把全局互斥锁（`std::mutex`），怀疑多 Agent
并发时互相排队，应做锁细化 / 连接池。

**测量工具**：[scripts/bench_concurrent.py](../scripts/bench_concurrent.py)（隔离数据目录 + 独立
platformd，播种 1000 条，1/2/4/8 个 worker 各一条 keep-alive 连接，每档 10 秒，
4/5 读 1/5 写；同机 12 核 Windows、Release 构建、本地 SSD，一次性测量）。

| 线程 | 吞吐 (req/s) | p50 | p95 | p99 | 错误 |
|---|---|---|---|---|---|
| 1 | 337.3 | 0.37 ms | 26.7 ms | 30.8 ms | 0 |
| 2 | 539.2 | 0.49 ms | 26.6 ms | 37.7 ms | 0 |
| 4 | **1044.2** | 1.33 ms | 22.2 ms | 37.3 ms | 0 |
| 8 | 936.1 | 5.63 ms | 31.6 ms | 42.9 ms | 0 |

**4 线程 / 1 线程 = 3.10x**（另一轮 500 行/6s 复跑为 4.43x）→ 按事前定的决策门
（≤1.30x 即立项）**混合负载通过，8 线程回落到 4 线程的 90%**（12 核机器，说明饱和点在 4–8 之间）。

把读写拆开，才能定位到真正的天花板：

| 负载 | 1 线程 | 2 线程 | 4 线程 | 4/1 比 |
|---|---|---|---|---|
| 纯读（keyword 检索，不经全局锁） | 424.5 | 1121.8 | **4020.7** | **9.47x** |
| 纯写（新建条目，全经全局锁） | 167.6 | 230.0 | **190.6** | **1.14x**（2 线程后反而下降） |

纯写 p50 从 1.6 ms（1 线程）涨到 18.3 ms（4 线程）——典型的串行排队。**所以缺陷是真的，
但只在写路径上**。于是必须回答"串行化来自锁，还是来自 SQLite/磁盘"。

**第二层证据**：[scripts/bench_sqlite_ceiling.py](../scripts/bench_sqlite_ceiling.py) 用 Python
标准库 sqlite3 复刻同样的写入形态（每条一个事务、2 个 INSERT、正文 ~900B），
**完全不涉及 Platform 的任何锁**，只改 SQLite 配置：

| 配置 | 吞吐 (txn/s) | p50 | p95 |
|---|---|---|---|
| A. WAL + `synchronous=FULL`，每条一事务（≈产品现状） | 636.4 | 1.55 ms | 2.53 ms |
| B. WAL + `synchronous=NORMAL`，每条一事务 | 12,175.0 | 0.04 ms | 0.11 ms |
| C. WAL + `synchronous=FULL`，20 条一事务 | 12,901.8 | 0.07 ms | 0.13 ms |
| D. WAL + `synchronous=NORMAL`，20 条一事务 | 110,870.9 | 0.01 ms | 0.02 ms |

A→B **19.1x**；A→C（同步等级不变，只做组提交）**20.3x**。

## 判定

* **全局锁不是瓶颈**。没有锁的裸 SQLite（A 组）在"每条一事务"形态下也只有 636 txn/s——
  这个上限对**任何**锁方案都成立；产品实测单线程 167 req/s 是 636 的 26%，差额来自
  一条知识写入还有 FTS 触发器、vec0 插入、嵌入计算、审计与 HTTP 链路，而**不是**锁竞争。
  纯写不扩展的直接原因是**每次提交一次 fsync**：磁盘本来就只能有一个写入者。锁细化
  无法改变这一点，投入产出比不成立。
* **该缺陷按原表述结案**（"全局互斥锁导致并发瓶颈"证据不成立）。已补测：
  4 线程混合负载 1044 req/s、0 错误，读路径近乎线性扩展（9.47x）。
* **真正值得做的是提交路径**，而且它带一个用户可见的取舍：

  1. **组提交**（把同一时间窗内的多个写请求合并进一个事务）：在 `synchronous=FULL`
     保持不动的前提下仍有 20x 上限空间，**不牺牲崩溃持久性**——这是首选方向。
     实现代价：需要把"写"重构为队列 + 单个提交线程，是跨模块改动（批次计划之外）。
  2. **放宽同步等级为 `NORMAL`**：再快 19x，但**断电/硬复位时最近若干次提交可能丢失**
     （WAL 模式下 NORMAL 不 fsync 每次提交）。这是持久性语义变更，**只能做成显式配置项
     并在 GUI 里写清代价**，绝不能默认打开。当前产品没有该开关，默认 FULL 是正确默认。

**结论与后续**：锁细化**不立项**（证据见上）；写提交路径的组提交**登记为后续立项候选**，
前置条件是把"写"收敛到单一提交点，属独立设计工作，不在本次最小计划范围内。
在预期负载（几个 Agent 以人的节奏写知识条目，即个位数 req/s）下，167 req/s 的单线程
写入上限有两个数量级余量，**当前不构成实际瓶颈**。

# 已知取舍与边界（集中声明）

以下各项经评估属"机制固有"或"窗口极窄"，**不作为缺陷处理**，在此集中声明以免反复被当成待修项：

| 项 | 取舍与理由 |
|---|---|
| Hermes 配置含块标量（`key: \|`）时整文件拒绝合并 | 块标量在场时"节边界"本身就不可信，局部扫描是自作聪明（fuzz 实测过）；拒绝后提示手工粘贴，不会写坏配置 |
| 同机任意进程可读 `config/agents.json` / `master.key` | 互信模型，README 已声明；审计在互信模型下防误操作、不防同机恶意进程 |
